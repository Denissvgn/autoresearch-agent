# Plan: Clean TRAID-platform artifacts from autoresearch-agent → universal research system

## Context & decisions

The repo is a half-finished generalization (ARC-011): a skill/manifest runtime with canonical `skill_id`/`subject_id`/`variant` vocabulary already exists end-to-end (dual-shape API aliases, `GET /api/v1/subjects`, manifest-driven command policy / preflight / promotion targets / metric schemas), and the neutral `prompt-engineering` skill proves the generic path works. The TRAID artifacts layer on top: 9 vendored platform packages, 3 trading skills, a legacy hardcoded ML path in the orchestrator, and platform service integrations.

Decisions (recommended options, no user override received):
1. **Trading skills removed entirely** — `prompt-engineering` stays as the exemplar.
2. **Platform service integrations removed from core** — capabilities become skill-manifest-declared; generic mechanisms (file-path/registry_api promotion, http/local_file preflight engine, static-token auth, optional OAuth2 introspection) remain.
3. **Legacy alias vocabulary kept** — `instrument`/`timeframe`/`model_type` keep working as aliases of `subject_id`/`variant`/`skill_id`; DB columns unchanged (no migration); per the documented backward-compat design.

Phases are ordered so each is independently shippable and tests stay green at every commit.

## Risks & mitigations
- **Test churn**: ~100/119 test files mention trading terms, but most only via the alias vocabulary (kept). True deletions are the ml-skill, pipeline, structured-hpo, ml-stack-contract, and gate-override test files; parity fixtures under `tests/parity/` need regeneration where they pin removed request fields.
- **Hidden consumers**: any missed import of a deleted module surfaces immediately in Phase 6's clean-venv install + full pytest; the domain-coupling guard prevents regressions afterwards.
- **Phase 1 is independently shippable** (pure dependency removal, no behavior change); Phases 2-3 land as separate commits so each revert point is green.
